# Agent 的持续进化：从"记住经历"到"学会成长"

> 基于李博杰《深入理解 AI Agent：设计原理与工程实践》第8章学习笔记
> 日期：2026-08-19

---

## 开篇：一万次错误还是第一天的错误

今天的 Agent 面临一个鲜明的能力悖论：**它可以零样本解决从未见过的复杂任务，却可能在处理了一万次相似任务之后，第二天仍然犯下第一天的错误。**

前几章讲的都是"会完成任务"：第二章的上下文工程让 Agent 在当前任务内适应，第三章的记忆库让它记得用户与世界是什么样的。但第 8 章要回答的是更本质的问题——**如何让 Agent 从"会完成任务"走向"能够可靠工作"**。核心是四个字：**持续进化**。

作者一开始就划清了一个容易混淆的界限：**保存经历 ≠ 从经历中学习。** 把一百条轨迹放进长上下文或向量库，只帮助模型在需要时找回某个案例，却不会自动完成跨案例比较——哪些步骤在成功轨迹中反复出现，某次成功究竟来自正确策略还是环境偶然。学习，发生在系统主动完成"评价、对照、归纳、验证"之后，而不是日志写入磁盘的那一刻。

更重要的是：**模型自身还不能可靠地持续学习。** 部署后的模型不会因为一次推理自动改变参数；生产环境又很少提供干净的学习信号——用户满意不代表合规，测试通过可能源于删除了失败用例。因此，现阶段最可行的路径，是在**模型外围构造一套自主学习系统**：记录运行证据 → 验证结果与过程 → 从多条轨迹提取共性 → 决定更新什么 → 经回归验证后发布。这套系统，就是图 8-1 所示的**持续进化闭环**。

## 一、起点不是"总结"，而是"评价"

持续进化的第一步不是让模型反思，而是先判断：**这次运行到底好在哪里、错在哪里？** 如果系统不知道任务是否完成，也不知道哪一步造成了成败，那么语言模型生成的反思只是一种猜测；错误的评价一旦进入长期知识，影响会跨任务不断放大。

### 三层轨迹验证

有的任务结果容易验证（Coding Agent 跑测试、退款 Agent 查订单状态），但**结果正确并不代表过程正确**——删除失败的测试用例也能让测试通过。因此可靠评价既要看结果，也要检查达成结果的路径。

图 8-2 给出了一个三层验证结构：

| 层级 | 验证器 | 回答的问题 | 主要证据来源 |
|------|--------|-----------|-------------|
| 底层 | 结果验证器 | 事情是否真的办成 | 测试结果、数据库状态、工具返回 |
| 中层 | 过程验证器 | 是否以允许的方式办成 | 业务规则、权限、动作序列 |
| 上层 | 质量验证器 | 是否办得合适 | LLM Rubric 逐项评分 |

**越靠下的指标越应依赖代码和环境真值，只有难以形式化的部分才交给语言模型。** 这不是说不能用 LLM-as-a-Judge，而是不能只让它给一个模糊总分——要预先定义 Rubric（评价量表），逐项给分、引用轨迹证据、证据不足时明确表示"不确定"。

### 客服 Agent 的 Rubric 维度

以客服为例，一套有用的 Rubric 至少覆盖表 8-1 的几个维度。前五项约束底线，后两项衡量服务质量：

- **任务结果**：核心诉求是否解决（看环境状态、工具结果）
- **规则遵从**：是否违反政策、权限、必要流程（看政策库、动作轨迹）
- **隐私边界**：是否泄露不该提供的信息
- **事实可靠性**：陈述是否有知识或工具结果支持（看引用来源）
- **承诺—行动一致性**：声称完成的操作是否真实发生（看回复与工具日志对照）
- **表达质量**：是否自然简洁、避免模板化（看语言 Rubric）
- **合规变通**：原方案不可行时，是否找到允许的替代路径

其中"**承诺—行动一致性**"尤其适合 Agent 场景——传统文本评价只读最终回复，容易把"我已经为你提交退款"当作良好服务；轨迹评价则继续检查是否真的调用了退款工具、订单状态是否改变。"合规变通"也不是鼓励突破规则，而是要求 Agent 理解用户真实目标，在退款不可行时寻找改签、延期等合法选项。

### 维度化信号与验证器校准

**验证结果不应压缩成一个标量。** 一次轨迹评价更像结构化诊断：任务部分成功、规则遵从通过，但有一处无证据陈述和一处虚假承诺。维度化信号保留了问题性质和证据位置，后续模块才能判断该补知识、改提示词，还是在 Harness 里加一致性检查。

LLM 验证器本身也需要校准：准备一小批专家标注轨迹，检查各维度一致性；高风险或低置信度案例交给第二个模型或人工复核；模型版本变更后重跑校准集。同时要注意——**验证器负责给评价和证据，修改 Agent 哪个部分应由独立的诊断模块决定，避免同一个模型既当裁判又直接改写规则。**

## 二、持续进化的四种方法：把经验写到哪里？

学习信号说明了"应当改变"，但没说改变发生在哪里。**选择更新方式的首要依据不是经验出现了多久，而是目标能力能否被某种载体自然表达。**

图 8-3 与表 8-2 给出了四种互补的载体：

| 更新方式 | 适合承载 | 主要优势 | 主要局限 |
|----------|---------|---------|---------|
| 经验知识库 | 事实、经验规律、例外与来源 | 更新快、可追溯、按需检索 | 依赖检索和模型正确应用 |
| Prompt 与 Skill | 可语言化的判断原则和操作规范 | 可解释、作用范围可控 | 容易膨胀、冲突或被忽略 |
| 程序与 Harness | 确定性流程、工具和强约束 | 可测试、执行稳定、成本低 | 开发与维护成本较高 |
| 模型参数 | 高维感知、生成风格和隐式策略 | 泛化能力强、推理开销低 | 更新与回归成本高 |

关键认知：**四种方式并不互斥，而是把每种能力放到最适合表达和治理它的位置。** 医疗影像 Agent 用参数识别病灶、用知识库提供最新指南、用代码计算风险；客服模型的自然语气来自后训练，企业政策由知识和 Skill 提供，关键合规则由服务端代码兜底。

### 8.2.1 将经验沉淀为知识

最轻量的进化方式，是把反复出现的经验整理成可检索的知识文档。它和第三章的记忆库共享存储与检索技术，但**来源和验证目标不同**：第三章提取"用户与世界是什么样的"，本章提取"在什么条件下应该怎样做"。例如"该航司要求特殊餐食提前 24 小时预订"是领域知识；"订票前先检查特殊餐食截止时间"才是行动经验。

**原始轨迹不适合作为正式知识单元。** 稳妥的系统保留三层数据：

1. 不可变的**原始轨迹**（用于审计）
2. 单次运行的**结构化分析**（记录成败与候选教训）
3. 多条同类轨迹**跨轨迹归纳**后形成的 Markdown 知识文档

正式文档写清适用场景、推荐策略、禁止做法、例外条件、证据来源和最近验证时间。真正有迁移价值的内容来自**对照**：同类成功轨迹做了什么，失败轨迹缺少什么；某种策略在哪些环境版本有效、在哪些前置条件失效。

一个完整的知识提炼管道分五步：保存不可变轨迹 → 单次结构化分析 → 按任务族聚合 → 达到支持门槛才写入正式文档 → 在新任务上测试迁移。GAIA 例子中，成功轨迹贡献候选策略、失败轨迹贡献排除性知识、部分成功轨迹帮助识别"哪段有效哪段还有问题"。**Reflexion 的自然语言反思可参与生成候选教训，但反思本身不是证据**——只有与环境结果相符、得到跨轨迹支持并显示正向迁移的内容才应进入正式文档。

### 8.2.2 将经验写成指令

当多条轨迹反复揭示同一种策略错误、且规律能用自然语言清楚表达时，可把经验从"可参考"提升为"应遵守"的规则。作用于几乎所有任务的规则进系统提示词；只在某领域/项目生效的复杂流程写成按需加载的 Skill。

**提示词学习**与第二章的提示工程分工不同：第二章回答怎样写出结构清晰的提示词，这里回答什么生产反馈足以触发修改、新规则怎样在部署前被验证。修改不应表现为反复重写整份系统提示，而应**根据一组同类失败生成最小 diff**，注明作用域、检查是否与现有规则矛盾、在边界案例和旧任务保留集上同时评估。

Andrej Karpathy 在 2025 年把这称为**系统提示学习（System Prompt Learning）**：预训练学知识、微调塑造习惯性行为，但人类还有一种学习——遇到问题、想通方法后，用明确的语言提醒未来的自己"下次遇到这类问题应先试这种办法"。他把缺少这种"记事本"的 LLM 比作电影《记忆碎片》的主角，并指出它与强化学习的区别：前者编辑文字，后者通过梯度下降修改参数。他举的例子是，当时 Claude 约 1.7 万词的系统提示中专门要求遇到字符计数问题时先逐项编号显式计数——正是为了处理"strawberry 里有几个 r"这类问题。

提示词自动优化已有几条路线：**DSPy**（把多模型调用程序视为可优化对象，在开发集搜索指令示例）、**OPRO**（让 LLM 根据历史提示词和得分提出候选）、**GEPA**（用失败轨迹的自然语言反思生成筛选候选）。它们面向离线评估集的批量优化；生产系统的**最小 diff 更像持续维护**——由新边界案例触发，强调来源、审计和快速回滚。

### 8.2.3 将经验写成程序

当经验描述的是稳定、重复、可验证的操作时，每次都让模型重新阅读文档推理并不经济。更合适的做法是把经验**编译为工作流、工具或 Harness 代码**，让一次探索变成可重复执行的程序。这就像电子表格的宏录制：第一次发送邮件时，多模态 Agent 靠观察—思考—行动寻找控件；以后再发邮件，流程没变，只是收件人和内容不同，没必要再从像素和 DOM 重新发现整条路径。

浏览器工作流编译有六步生命周期：

1. **捕获轨迹**：记录导航、点击、输入等动作，保存参数、URL 和 XPath/CSS/id/role 等定位证据（定位信息只用于再次找元素，不能证明任务完成）
2. **参数化**：把字面量识别为模板变量（`{recipient}`、`{subject}`），稳定动作保持不变
3. **定义状态检查**：动作前检查（按钮可见）、动作后检查（URL 属于目标站点）、最终状态检查（已发送列表出现新邮件）——**动作执行成功与任务成功是两件事**
4. **候选验证**：首次成功只生成 candidate，沙盒重置后完整回放，全部检查通过才发布为 validated；有副作用任务若无安全重置回调只能存候选供审计
5. **匹配与回放**：新任务按意图匹配工作流、提取参数，由 Playwright 直接执行，回放不逐步调用 LLM
6. **失效与重学**：找不到元素、检查不通过、API 变化时停止后续动作，旧版本移入 invalid 区，回退到完整 Agent 重新探索

**PreAct** 实验中，这类程序在重复任务上实现 8.5~13 倍端到端加速。更重要的教训是：流程记忆必须同时具备动作前验证、动作后验证和存前独立验证，否则会得到危险假象——回放覆盖率 100%、每个按钮都点过了，但某个字段其实为空。

**Agent 修改自己的代码，不意味着运行中进程直接覆盖自身。** 生产系统应从稳定版本创建候选分支，由 Coding Agent 生成最小补丁，依次通过静态检查、单元测试、安全扫描、失败轨迹重放、旧任务回归，再灰度部署。这就是第 8 章与第 5 章的边界：**第 5 章提供修改系统的能力，本章提供由经验触发、以验证闭环约束的自我修改方法。**

每个修改请求还应是一份**可证伪的变更契约**：列出失败证据、推断根因、归属的 Harness 组件、候选修改、预期修复的行为、可能受损的既有行为及验证用例。候选生成器的输入也不应只有失败案例——**Self-Harness** 还提供必须保留的成功行为和此前被拒绝的修改记录，避免 Agent 换种说法重复提交已失败的方案。

### 8.2.4 将经验写入参数

知识、指令和程序都建立在一个前提上：**目标能力能被外部符号较完整表达**。但医疗影像理解、自然的语音韵律、消除"AI 味"、长程规划等能力很难压缩成几条规则或工作流，必须通过后训练写入参数。

是否参数化**不由"任务是否长期稳定"单独决定**：新影像设备带来的域偏移可能仍需 LoRA 持续微调，快速变化的语言风格可通过周期性偏好训练适应；反过来，长期稳定的转账审批规则不应只靠参数记忆，服务端代码仍需提供确定性保障。**稳定性影响更新频率和成本，但能力的表示性质决定主要载体。**

第 7 章已完整讨论 SFT、蒸馏、RL，本节不重复。对持续进化而言，关键是把经过评价的生产轨迹转化为训练数据：高质量示范进 SFT、明确偏好形成成对数据、有可靠环境奖励的交互用于 RL。进入训练前要除隐私、滤错误轨迹、留独立回归集；训练后检查通用能力和安全对齐是否遗忘。

### 8.2.5 从更新产物到更新"更新方法"

持续进化还有一条正交的轴：系统优化的究竟是某份产物内容，还是**产生、管理和验证这些产物的方法**。沿这条轴，优化对象可逐层扩大：

> 单条规则/记忆 → 结构化上下文 → 工作流 → Harness 代码 → 优化器代码

这不是五种新载体，而是**五种不同的搜索尺度**。最内层只改产物内容，作用面小、易归因回滚，是默认选择。但反复重写整份 Prompt 会退化：旧版本的重要细节在改写中消失，相互制约的条件被合并成过度抽象的原则。

于是出现更外层的优化：**Agentic Context Engineering（ACE）** 把上下文维护成带稳定标识符的条目集合，用生成、反思、整理模块提出增量更新，再用确定性逻辑合并去重，而不是每轮重写一个越来越短的文本块。**Meta Context Engineering（MCE）** 拆成内外两循环：内层在给定管理方法下优化当前任务产物，外层根据多轮执行结果修改搜索、选择、过滤、格式化这些操作本身。同样思想扩展到工作流（**AFlow** 用执行反馈搜索代码图中节点与控制流组合）和整个 Harness（**Meta-Harness** 让 Coding Agent 搜索决定信息如何存储、检索、呈现的代码）。

但**优化层级并非越高越好**：搜索完整工作流或 Harness 要面对更大候选空间、更高评估成本、更严重归因困难。一个明确、反复出现、能定位到单一组件的故障，应优先做可审计的局部补丁；只有局部修改长期无法解决跨组件问题，才值得上升层级。无论上升到哪层，**评价器、权限边界和留出测试都必须位于可修改范围之外**——搜索空间越大，这个"可信根"越重要。

## 三、双循环：在线执行与离线进化

四种更新方式只有进入同一个自主循环，才会从单次优化变成持续进化。图 8-5 展示了生产系统中更稳妥的**双循环结构**：

```
在线执行循环              离线进化循环
稳定版Agent               聚合与诊断
   │                     寻找共同根因
   │ 记录轨迹与反馈           │
   ↓                     候选修改
版本化经验日志      ←→    知识·指令·程序·参数
   │                     回归与安全验证
   │                     保留旧能力
   ↓                     灰度、监控与回滚
通过验证的新版本  →        晋升为新稳定版

可信根：权限、审计、验证与回滚机制不由普通进化流程自行修改
```

**在线执行循环只完成任务并记录证据，不直接改写正式 Agent；离线进化循环聚合轨迹、诊断根因、生成候选修改，通过验证门槛发布新版本。** 两者通过版本化经验库和评估集连接。

**Voyager** 展示了较完整的持续进化循环：在 Minecraft 中根据当前能力选新目标，通过环境反馈迭代程序，验证成功后把代码存入技能库，再组合旧技能解决更难任务。它由三个机制咬合：**自动课程生成器**（提难度适中的下一个目标，避免随机漫游）、**技能库**（把成功程序存为可检索可组合的代码）、**迭代提示机制**（把环境观察、错误、自验证结果带回下一轮生成）。论文报告相比基线获得 3.3 倍独特物品、探索 2.3 倍距离、解锁科技树最快快 15.3 倍。作者强调：**自动课程、可执行技能、环境验证缺一不可**——只有技能库没有课程，Agent 不知道下一步学什么；只有反思没有环境验证，技能库会积累错误。

### 8.3.1 从问题定位到经验沉淀

同一个表面问题可能需要不同的修改方式。客服 Agent 出现幻觉，可能是缺知识，也可能只是 Prompt 没要求引用；没完成任务就作出"已经完成"的虚假承诺，既可用指令纠正，也可由 Harness 强制检查回复与工具状态。**进化模块应先定位根因，再选择最小、最容易验证和回滚的修改对象。** 证据不足的偶发故障不应立即触发学习，而应继续积累样本。

这种选择也随经验增加而变化：新策略先作经验文档供检索，多案例反复验证后提升为知识。知识有三种表达：规则能清晰表达则沉淀为 Skill；步骤稳定无需语言理解则编译成工具代码；反映广泛隐式决策能力则进入后训练。

### 8.3.2 验证、发布与回滚

所有修改首先产生**候选能力或候选 Agent**，而非直接覆盖生产版本。知识文档验证检索后是否提高新任务表现；Prompt/Skill 检查边界案例与旧任务回归；程序在沙盒和重置环境运行测试；参数更新检查遗忘、安全和分布外任务。验证通过后仍要**灰度发布**观察真实流量，关键指标恶化时自动回滚。

验证还要区分两种经常混在一起的能力：

- **Harness 更新能力（harness-updating）**：从轨迹中产生有价值的持久修改
- **Harness 受益能力（harness-benefit）**：任务 Agent 在后续运行中找到、激活并正确使用这些修改

一个 Skill 可能写得完全正确，但较弱的任务模型没在合适场景加载它，最终成绩看起来就"没有进化"。因此**不能只用端到端分数反推更新器好坏**。诊断时固定同一份候选 Harness 只替换任务模型：强模型受益而弱模型从不激活新产物，瓶颈在检索或路由；两者都激活但只有强模型正确执行，瓶颈在指令遵循或长程规划；所有模型都退化，才怀疑修改本身。**双向模型替换**比观察一个"进化后总分"更容易定位能力预算该放哪。

评估不是学习结束后的考试，长期评价至少同时观察五类结果：**回退（regression）、泛化、Token 效率、安全性、长期工程质量**。只解决当前失败却在其他案例退化，不是成功的持续学习。

### 8.3.3 可验证闭环的边界：当"完成"不等于"进步"

前面的闭环在 Coding、工具调用、业务状态变更上最容易成立，因为测试或环境状态能快速反馈。**开放式科研、战略规划、复杂产品设计则不同**：信号来得慢、正确答案不唯一、真正重要的目标（研究品味、长期价值、可维护性）很难写成即时分数。此时 Harness 可能把流程执行得非常完整，却只是稳定地产出"像成果的东西"。

自动科研是有代表性的压力测试。一次四次端到端尝试中三次失败的记录暴露三类问题：

1. **实现漂移**：原方案变难时，Agent 逐渐退回训练数据中更熟悉但偏离研究假设的普通实现
2. **认识论过度乐观**：信号可能只是噪声，系统却开始解释结果、加补丁、宣布发现；失败和阴性结果更易被忽略
3. **隐性判断力不足**：Agent 能跑实验，却未必知道什么基线重要、哪个异常值得追踪、何时该放弃假设

这类任务不能靠换更会写论文的模型解决，而要改变证据和监督结构：**结论与证据分离**（ScientistOne 的 Chain-of-Evidence 把每类声明链接到可审计来源）、**保留负面结果**（失败实验写入不可变日志，否则进化模块会反复探索已证伪路径）、**维护搜索多样性**（保留暂时低分但不同质的分支，避免收敛成易得分模板）、**让人类在更高层介入**（定义问题、审查评价标准、决定何时停止）。

持续进化的上限，最终取决于**系统能否评价它真正关心的目标，而不只是最容易测量的代理指标。**

### 8.3.4 持续进化的安全边界

自我进化能力可能把一次错误变成长期风险：提示注入被总结成经验会跨会话生效、恶意软件包被封装成工具会扩散到所有后续任务、有缺陷的验证器可能持续批准看似进步实际退化的候选。因此除了验证"是否更强"，还必须限制"谁能改什么、依据来自哪里"。

三道安全边界：

1. **证据与指令隔离**：原始网页和工具输出是不可信证据，须经 LLM 总结才能写入 Skill；写入用版本控制，提交 PR 经不同源 reviewer LLM 审阅后合入
2. **候选与正式能力隔离**：新知识、Prompt、Skill、程序、参数先进不可服务真实流量的候选区；新代码和外部依赖过沙盒、权限检查、供应链扫描、行为测试后才服务真实流量
3. **安全机制不可自我修改**：业务 Agent 可改 Prompt/Skill/知识库/工具，但不能修改批准自身更新的验证器、测试用例、发布门槛、审计日志、稳定版本备份——否则只需降低测试阈值就能把退化伪装成进步

### 8.3.5 睡眠学习：整合、遗忘与能力保鲜

"睡眠学习"是对离线整合的认知类比，不要求任务真在夜间运行。**在线 Agent 的首要职责是完成当前任务并追加不可变证据；后台学习进程则在空闲期或满足门控条件时读取一批新经历，比较新旧结论、合并重复项、解决冲突、提出候选更新并运行回归。** 把采集与整理分开，可防止一次偶发成功或恶意输入立刻改写长期能力。

一个典型睡眠学习周期五步：**触发**（达时间/数量/容量/错误率门槛且无高优在线任务）→ **定向**（读取已有能力与不可修改边界）→ **采集与整合**（找新信号、合并重复、标记冲突、优先生成局部补丁）→ **验证与审批**（在迁移/保留/安全集评估，高风险等人工批准）→ **修剪与索引**（过期或被推翻能力标为过期/归档/删除，保留来源与回滚版本）。

**Hermes** 给出完整后台进化案例：有界的 MEMORY.md 与 USER.md、基于 SQLite/FTS5 的历史会话检索、按需加载的 Skill，历史检索返回原始消息而非先由 LLM 摘要（避免把检索和生成混成不可审计步骤）。后台复盘可创建或局部修订 Skill，记忆和 Skill 写入经审批门控；**Curator** 跟踪 Skill 使用、陈旧、归档状态，空闲期执行确定性修剪。变更前保存快照，错误整理可回滚。

持续进化也不是让知识无限增长。**上下文腐化会在更长时间尺度上重现**：经验文档冲突、Prompt 被边界规则淹没、Skill 库重复、多次微调造成灾难性遗忘。系统需周期性离线整理：合并重复经验、把局部规则从全局 Prompt 移到领域 Skill、保持 Prompt 结构清晰（避免"99 条军规"式罗列）、重新验证长期未用工具、删除被推翻的知识、从原始基座重训 LoRA。

## 四、本章小结

- **持续学习正在成为 Agent 最重要的能力之一，但今天的模型还无法自行完成可靠的持续学习。** 推理时的上下文适应不会自动持久化，未经验证的在线参数更新又会放大噪声、攻击和能力漂移。现阶段更可行的路径，是在**模型外围建立可验证的学习系统**。
- Agent 从与环境交互和评价中获得学习信号，再根据**能力的表示性质**更新知识、Prompt、Skill、程序或模型参数。系统可进一步优化管理和生成这些产物的方法，但**应优先采用可归因、可验证、可回滚的局部修改**。
- 持续进化需要把**在线执行与离线学习分开**：在线记录证据，离线生成并验证候选更新，再逐步发布、整理或回滚。这个闭环在结果可自动验证的任务上最可靠；对目标模糊、反馈延迟的开放任务，**人仍需参与问题定义和评价标准的制定**。

## 总结：一张持续进化的全景图

第 8 章把前七章组装成一个完整闭环：**第 2 章处理任务内状态，第 3 章提供知识基础设施，第 5 章赋予创造工具和修改系统的元能力，第 6 章建立评估验证，第 7 章说明如何更新参数，第 8 章把这些部件组织成持续进化系统。**

对工程师最实用的四条提醒：

1. **评价先于总结**：没有可靠的轨迹评价，反思只是猜测；用三层验证（结果→过程→质量）把信号变结构化诊断
2. **载体由能力决定**：事实进知识库、可语言化原则进 Prompt/Skill、确定性流程进程序、高维能力进参数——四种方式互补不互斥
3. **局部优先、可信根保护**：优先最小可归因补丁；评价器、权限、留出测试永远在可修改范围之外
4. **闭环而非补丁**：把在线执行与离线进化分离，验证—发布—回滚循环才能让单次优化变成持续进化

模型自身目前还不能可靠持续学习，但**"在模型外围构造可验证的学习系统"这一工程路径，已经在 Voyager、Hermes、PreAct 等系统中被证明可行**。这或许就是下一代 Agent 从"聪明"走向"熟练"的关键一步。
