# TypeScript 学习笔记（17/17）：类型声明与读懂报错——收官篇

> 对应书源：TypeScript Handbook「Type Declarations」+「Understanding Errors」全篇｜系列第 17 篇（最终篇）

## 开篇：你写的代码之外，还有半个世界

前十六篇里，`Math.max`、`window`、`Array.push` 这些 API 的类型信息我们用得心安理得——可它们的实现从没出现在我们的代码里。TS 是怎么知道 `Math.mix` 不存在而 `Math.max` 存在的？答案是**声明文件**。同时，写 TS 绕不开的日常是被报错信息轰炸——动辄十几行的错误墙怎么读？收官篇把这两块拼图补上，然后为全系列画一张地图。

## 一、`.d.ts`：只说类型，不给实现

TS 有两种主要文件：

| 文件 | 内容 | 产出 |
|---|---|---|
| `.ts` | 类型 + 可执行代码（实现文件） | 编译出 `.js` |
| `.d.ts` | **只有类型信息**（声明文件） | 不产出任何 `.js` |

声明文件提供了一种"**声明某些类型或值存在、但不提供实现**"的方式。`Math`、`window`、`document` 的类型全部来自 TS 内置声明文件，命名模式为 `lib.[something].d.ts`——见到这个模式就知道面对的是平台内置部分而非用户代码。

## 二、`target` 与 `lib`：内置 API 的可用性开关

内置 API 的可用性随 JS 版本变化：字符串的 `startsWith` 方法是 ES6 才有的，部署到更老的平台就是运行时事故。TS 用两道闸门管理这件事：

- **`target`**：决定按哪个 JS 版本对待代码——设为 `ES5` 时使用 `startsWith` 直接报错，因为该方法所属的 lib 定义在 ES5 档不包含。TS 会根据 `target` 自动调整默认包含哪些 lib 文件。
- **`lib`**：更细粒度的手动控制，指定哪些内置声明文件可用（比如在 Node 项目里去掉 DOM 类型，避免误用 `window` 还不自知）。

## 三、外部类型的三种来源

第三方库的类型从哪来？按优先级有三条路：

1. **Bundled Types**：库自己随 npm 包发布声明文件——导入后 TS 能自动解析出类型就说明有，无需额外步骤，如今主流库基本走这条路。
2. **DefinitelyTyped / `@types`**：集中存放数千个库声明文件的大型仓库，自动发布到 npm 的 `@types` scope，**包名与原包名一致**。装了 `react` 没带类型，就 `npm install --save-dev @types/react`。TS 自动发现 `node_modules/@types` 下的定义，零配置生效。
3. **自己写**：冷门库既不带类型也没上 DefinitelyTyped 时可自己写声明文件；只想快速消音的话，一行空声明把模块标成 `any`：

```ts
declare module "some-untyped-module";
```

## 四、读懂报错：先学一个词

### "assignable to"：可赋值性

TS 判定一个类型 **assignable to** 另一个类型，标准是"前者是否可作为后者的合格替身"：`Cat` 可赋值给 `Animal`，因为猫能顶替动物的位置。这个关系用于检查赋值语句 `t = s;`，也用于检查几乎所有类型交互——比如调用函数时，每个实参的类型必须可赋值给形参的声明类型。

两件事要记住： informal 地看，"`T` is not assignable to `S`" 就是"**`T` 和 `S` 不兼容**"；而且这是**有方向的**——`S` 可赋值给 `T` 不代表 `T` 可赋值给 `S`（动物能顶替猫的位置吗？未必——动物不一定会喵喵叫）。方向性在排查赋值报错时非常关键：先确认报错里谁是源谁是目标，再谈兼容。

### Error Elaborations：报错是一串"为什么"

每条报错以主消息开头，后面可能跟着若干子消息——**每个子消息都在回答上一条消息的"为什么"**。看这个比报错还短的例子（错误 2322）：

```ts
let a: { m: number[] };
let b = { m: [""] };
a = b;
```

TS 的推理链是：`b` 的类型可赋值给 `a` 吗？不能。为什么？`m` 属性类型不兼容。为什么？`b` 的 `m`（`string[]`）不能赋值给 `a` 的 `m`（`number[]`）。为什么？数组元素类型 `string` 不能赋值给 `number`。**从下往上读**往往最快定位根因——最后一条子消息才是最具体的病因。

### 两个典型报错样本

**多余属性**（错误 2322）：`type A = { m: number }` 下 `const a: A = { m: 10, n: "" }`——报错指出 `n` 不存在于类型 `A`，正是 052 篇"新鲜度检查"在报错层面的呈现。

**联合赋值**（错误 2322）：`type Thing = "none" | { name: string }` 下 `const a: Thing = { name: 0 }`——TS 会分别对照联合的每个成员说明为何都不匹配（不是 `"none"`；`name: number` 不满足 `{ name: string }`），错误墙虽长，每个分支都是一条独立线索。

结构化类型系统的报错天然冗长，因为它要把"结构哪里不匹配"层层展开。冗长是特性不是缺陷——耐心读完子消息链，答案通常就在最后一行。

## 实践建议

1. **先查库自带类型，再找 @types，最后才手写**：顺序别反，`declare module "..."` 是消音不是方案。
2. **`target` 定运行平台，`lib` 管类型环境**：Node 项目记得剔除 DOM，避免 `window` 误用。
3. **报错从最后一行子消息开始读**：那里是最具体的病因，主消息往往只是结论。
4. **牢记 assignable 的方向性**：排查"为什么不能赋值"时先确认方向。
5. **把错误码当检索键**：2322、2339、2345……错误码 + 关键字搜索，绝大多数疑问早有人问过。
